# PicBind Tauri AI Coding 规范

> 适用版本：0.1.0
> 适用阶段：Tauri 持续开发与图片 Native Store V2
> 目标读者：参与本阶段开发、检查和修复的 AI 编程助手

## 1. 规范目标

本规范用于约束后续 AI Coding 的实现范围和工作方式。Tauri 框架接入阶段已经完成；
当前图片存储目标是：

> 保持 UI 和业务契约稳定，通过统一 `ImageStorageRepository` 接口让 Web 使用 Dexie +
> OPFS、Tauri 使用 SQLite + 应用数据目录。

桌面差异只能在已经确认的图片存储范围内实施。不得借此扩展页面交互、压缩算法、
网络流程或其他本地状态。

## 2. 指令优先级

开始编码前，AI 必须按以下顺序读取并执行约束：

1. 用户在当前任务中提出的明确要求。
2. 仓库根目录 `AGENTS.md`。
3. `docs/architecture/desktop/README.md` 中的版本范围和完成标准。
4. 本文档。
5. 仓库现有代码、依赖和工程惯例。

如果这些约束之间存在冲突，必须停止扩大改动范围，说明冲突并等待确认。不得自行
选择会改变产品行为的方案。

## 3. 当前硬性边界

### 3.1 必须完成

- 保持现有 Tauri 工程和本地开发流程可运行。
- Tauri 产品版本统一为 `0.1.0`。
- 使用现有 `apps/web/` 应用作为唯一前端来源。
- Web 图片缓存继续使用 Dexie + OPFS。
- Tauri 图片缓存通过独立 Tauri Repository 使用 SQLite + 应用数据目录。
- 原生 command 不接受任意路径、任意 SQL 或 Shell 命令。
- 保持 Web 版版本为 `1.0.8`。

### 3.2 禁止实施

- 禁止复制一份 Web 页面作为桌面版页面。
- 禁止在页面组件或业务 Store 中散落 `isTauri`、User-Agent 或平台检测分支。
- 禁止在业务 Repository 中判断运行环境；平台选择只能出现在统一 selector。
- 禁止 Web Repository 导入 Tauri IPC，或 Tauri Repository 导入 Dexie/OPFS。
- 禁止新增桌面专属页面、按钮、菜单、托盘、快捷键或通知。
- 禁止接入原生文件选择、文件保存、目录遍历或 Shell 命令。
- 禁止修改图片压缩算法、编码器、参数、质量判断或回退规则。
- 禁止改变 Web 的 Dexie + OPFS 行为；localStorage 和 sessionStorage 不属于本任务。
- 禁止改变现有 API、Room、WebRTC 或其他网络请求流程。
- 禁止修改 Web 版版本号、部署配置或 Cloudflare 发布流程。
- 禁止把签名、自动更新和正式安装包发布带入图片存储任务。

### 3.3 需要先确认的改动

遇到以下情况时，AI 必须先说明原因、影响和可选方案，获得确认后再实施：

- 必须修改现有 Web 业务代码才能启动 Tauri。
- 必须改变 Web 构建方式或静态部署结果。
- 必须引入 Tauri 原生插件或扩大权限。
- 必须修改压缩行为或 WASM API。
- 必须把 Web/Tauri 图片存储差异扩大到 Repository 之外。
- 必须调整 `0.1.0` 或 Web `1.0.8` 版本号。

## 4. 工程设计规则

### 4.1 最小接入

- Tauri 承担桌面窗口、应用生命周期和已确认的原生图片存储职责。
- 优先通过配置连接现有 Web 开发服务，不为接入 Tauri 重写前端。
- Tauri Rust 入口只注册已确认的原生能力；图片 command 必须保持业务级、有限范围。
- 工程目录应与 `apps/web/`、`packages/`、`crates/` 保持清晰边界。
- 不移动现有目录，不进行与接入无关的仓库重构。

### 4.2 依赖管理

- 使用与仓库现有工具链兼容的 Tauri 稳定版本。
- JavaScript 包与 Rust crate 的 Tauri 主版本必须匹配。
- 新依赖必须是框架运行、已确认 Native Store 或原生下载所必需的，并说明用途。
- 使用现有包管理器和锁文件，不混用 npm、Yarn 与 pnpm 锁文件。
- 不进行顺手升级，不批量更新无关依赖。
- 生成的锁文件只允许包含本次必要的依赖变化。

### 4.3 版本管理

- 所有 Tauri 产品版本配置必须保持 `0.1.0`。
- `apps/web/package.json` 必须继续保持 `1.0.8`。
- Tauri 与 Web 的版本不得通过同一个自动同步脚本绑定。
- 包名、bundle identifier 等稳定标识一旦确定，不得在无需求时反复修改。

### 4.4 安全与权限

- 使用最小权限原则，只开启窗口加载现有前端所需能力。
- 不启用 Shell、文件系统、进程、剪贴板或网络访问插件，除非任务明确要求。
- 不使用通配权限代替具体权限。
- 不为了绕过启动问题而关闭全部 CSP 或安全限制。
- 不把密钥、Token、本机绝对路径或个人环境配置提交到仓库。

### 4.5 跨平台原则

- 不针对 macOS、Windows 或 Linux 编写图片存储业务分支。
- 路径通过构建工具和 Tauri 配置解析，不在代码中写死个人绝对路径。
- 不假设目标机器已经全局安装项目私有依赖。
- 当前只需验证开发机器；不得把未验证的平台写成已支持。

## 5. 编码流程

后续 AI 必须按以下顺序执行实现任务：

1. 检查工作区状态，识别并保留用户已有修改。
2. 阅读存储架构文档、相关 Repository 和 Rust storage 实现。
3. 明确本次能力属于已实现基础层还是后续 V2 阶段。
4. 保持 Repository 的业务契约，平台选择不得泄漏到 UI。
5. 安装或解析必要依赖，并检查锁文件只包含预期变化。
6. 为元数据、文件写入、读取、覆盖和删除补充适量测试。
7. 验证 Web 与 Room SDK 类型，再验证 Rust 格式、编译和测试。
8. 实际启动 Tauri 客户端，检查窗口、IPC 和应用数据目录。
9. 停止测试进程，确认没有遗留开发服务或客户端进程。
10. 根据真实结果同步文档，最后检查完整 diff。

不得只生成脚手架就宣称完成，也不得只看到编译成功就代替客户端运行验证。

## 6. 代码和配置要求

- 遵循现有文件的格式、命名和缩进风格。
- 配置项使用框架支持的正式字段，不使用未经验证的自定义字段。
- 对版本、开发服务地址、构建输出目录等关键配置保持单一来源。
- 不提交 Next.js `.next/`、Rust `target/` 或本机生成的临时文件。
- `.gitignore` 只增加实际产生且确需忽略的条目。
- 代码注释只解释不明显的约束，不重复描述代码本身。
- 错误必须保留有效上下文，不使用空 `catch` 或静默忽略启动失败。

## 7. 验证要求

AI 必须根据实际工程执行所有适用检查，并记录真实结果。

### 7.1 静态检查

- Tauri、Cargo 和前端配置能够被对应工具正确解析。
- Rust 代码通过格式检查和编译检查。
- Web 原有 TypeScript、lint 或构建检查没有因本次接入新增错误。
- `git diff --check` 通过。

### 7.2 版本检查

- Tauri 配置中的产品版本为 `0.1.0`。
- Tauri Rust 包版本为 `0.1.0`。
- 如果存在独立 Tauri 前端包，其版本为 `0.1.0`。
- `apps/web/package.json` 仍为 `1.0.8`。

### 7.3 运行检查

- 使用文档中的命令能够启动 Web 开发服务和 Tauri 客户端。
- 客户端主窗口成功出现，不是空白页或错误页。
- 首页能够正常渲染和操作。
- 现有主要页面能够打开。
- 开发终端和 WebView 控制台没有阻断使用的错误。
- 关闭客户端后相关进程能够正常退出。

如因当前环境无法进行 GUI 验证，AI 必须明确报告未验证项及原因，不得把它标记为
通过。

## 8. 回归保护

- Tauri 改动前后，Web 版使用原命令仍可独立启动和构建，并继续使用 Dexie + OPFS。
- Web 版不依赖 Tauri CLI、Rust 进程或本地客户端才能运行。
- Tauri 开发命令不得永久占用或修改 Web 的生产配置。
- 不修改压缩行为，因此本阶段原则上不需要重建 WASM；一旦修改 Rust 图片处理或
  WASM API，必须停止并按根目录 `AGENTS.md` 的完整流程处理。

## 9. 文档同步

完成 Tauri 接入时，AI 必须同步维护：

- `docs/architecture/desktop/README.md`：将已经完成的能力与仍在规划的能力准确区分。
- `docs/architecture/desktop/development.md`：记录环境要求、安装步骤、开发命令和常见问题。
- `docs/architecture/desktop/tauri-storage-architecture-v2.md`：同步图片存储现状、边界和实施状态。
- 仓库入口文档：仅在用户要求或实际开发入口发生变化时更新。

文档只能描述已经验证的命令和行为，不得把计划能力写成已实现。

## 10. 完成交付格式

AI 完成编码后必须向用户说明：

1. 新增和修改了哪些文件，以及每项改动的目的。
2. Tauri `0.1.0` 与 Web `1.0.8` 的版本核对结果。
3. 实际执行了哪些检查，结果是否通过。
4. Tauri 客户端是否在本地 PC 上实际启动成功。
5. 尚未验证的内容、已知限制和下一步边界。

不得使用“应该可以运行”代替真实验证结果。
